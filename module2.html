Why Domain-Specialized Models?

General-purpose LLMs (GPT-5, Claude 4.5) are powerful, but they lack deep familiarity with hardware description languages, EDA tool syntax, and SPICE conventions. Domain-specialized models bridge this gap by training on curated hardware corpora — achieving dramatically better results on RTL generation, netlist analysis, and design script tasks.

🔵 Key Finding from Research

RTLCoder, a 7B-parameter model, outperforms GPT-3.5 on RTL generation benchmarks while running locally on just 4GB of RAM. Domain specialization is more efficient than raw model size for EDA tasks.

💬
ChatEDA
Three-stage pipeline: task decomposition → script generation (Python/Tcl) → task execution. Uses AutoMage as its specialized controller model.

RTLCoder
Lightweight, privacy-preserving RTL generation. 7B params, runs locally. Quality-based training with simulator feedback for synthesizable outputs.
🧠
EDAid
Multi-agent divergent thought collaboration. Multiple ChipLlama agents use different CoT prompts to explore diverse design pathways.

ChatEDA and the AutoMage Controller

ChatEDA represents one of the first production-grade LLM-powered autonomous agents for EDA. It transforms natural language design specifications into executable EDA tool flows, closing the gap between intent and implementation.

The Three-Stage Pipeline

Stage 1
Task Decomposition
The AutoMage controller receives a natural language specification (e.g., "Synthesize this RTL for a 28nm TSMC process targeting 500MHz") and decomposes it into a structured list of atomic EDA tasks with dependencies. This is analogous to the Supervisor pattern from Module 1.
Stage 2
Script Generation (Python/Tcl)
For each decomposed task, AutoMage generates the corresponding EDA tool script — Tcl for synthesis flows, Python for post-processing. The model has been trained specifically on EDA tool APIs (Synopsys DC, Cadence Innovus, OpenROAD).
Stage 3
Task Execution & Feedback
Scripts are executed in an EDA tool environment. Output logs are parsed by AutoMage, which identifies errors and updates the task plan accordingly. This creates a closed-loop generation-execution-refinement cycle.

AutoMage: The Controller Model

AutoMage is an expert model fine-tuned on Llama 2 using a sophisticated self-instruction paradigm. Rather than expensive human annotation, the training dataset was generated synthetically using GPT-4.

💜 Self-Instruction Paradigm (Key Innovation)

GPT-4 was used to generate a 10,000-tuple training dataset in the format: <requirement, decomposition, script>.

  • requirement: Natural language design task (e.g., "run timing analysis with clock uncertainty 100ps")
  • decomposition: Structured breakdown into atomic subtasks
  • script: The correct Tcl/Python EDA script for each subtask

This approach allows training a specialized expert model without requiring expensive domain expert annotation at scale.

Python — ChatEDA-style Pipeline Implementation 
from langchain_community.llms import Ollama
from langgraph.graph import StateGraph
from typing import TypedDict, List

class ChatEDAState(TypedDict):
    requirement: str
    subtasks: List[dict]
    scripts: List[str]
    execution_logs: List[str]
    completed: bool

# AutoMage-style decomposition (using fine-tuned Llama)
automage = Ollama(model="automage-llama2-7b")

def decompose_task(state: ChatEDAState) -> dict:
    """Stage 1: Decompose NL requirement into subtasks."""
    prompt = f"""You are an EDA expert. Decompose this requirement into atomic EDA tasks:
    
Requirement: {state['requirement']}

Output JSON list with fields: task_name, tool, description, dependencies"""
    
    response = automage.invoke(prompt)
    subtasks = parse_json(response)
    return {"subtasks": subtasks}

def generate_scripts(state: ChatEDAState) -> dict:
    """Stage 2: Generate Tcl/Python scripts for each subtask."""
    scripts = []
    for task in state["subtasks"]:
        prompt = f"""Generate a {task['tool']} script for: {task['description']}
        Output ONLY the executable script, no explanation."""
        script = automage.invoke(prompt)
        scripts.append(script)
    return {"scripts": scripts}

def execute_and_verify(state: ChatEDAState) -> dict:
    """Stage 3: Execute scripts and capture feedback."""
    logs = []
    for i, (task, script) in enumerate(zip(state["subtasks"], state["scripts"])):
        log = run_eda_tool(task["tool"], script)
        logs.append(log)
        if "ERROR" in log:
            # Trigger re-generation for this specific subtask
            return {"execution_logs": logs, "failed_subtask": i}
    return {"execution_logs": logs, "completed": True}

# Build ChatEDA workflow
workflow = StateGraph(ChatEDAState)
workflow.add_node("decompose", decompose_task)
workflow.add_node("generate", generate_scripts)
workflow.add_node("execute", execute_and_verify)

RTLCoder: Lightweight Verifiable Synthesis

RTLCoder addresses a critical gap in EDA AI: the need for a locally deployable, IP-privacy-preserving model for RTL code generation that produces synthesizable (not just syntactically correct) Verilog.

📦
Model Specifications
  • 7B parameters — Deepseek or Mistral base
  • Runs on 4GB RAM — laptop-deployable
  • Fully open-source weights
  • No cloud API calls required
🎯
Key Innovation
Quality-Based Training Scheme uses actual simulator feedback (Icarus Verilog) to reward synthesizable code during training — not just syntactically correct code.
🏆
Performance
Outperforms GPT-3.5 on RTL generation benchmarks despite being dramatically smaller. Competitive with GPT-4 on synthesizability metrics.

Quality-Based Training Scheme

The core innovation of RTLCoder is how it trains: using dual feedback signals from actual EDA tools to distinguish truly synthesizable code from merely syntactically valid code.

The Quality-Based Training Pipeline

Standard instruction fine-tuning rewards code that looks like Verilog. RTLCoder's quality-based training rewards code that actually works in a simulator:

  1. Generate candidates: For each RTL specification, generate N candidate solutions using the current model checkpoint.
  2. Syntax check: Pass each candidate through Icarus Verilog (iverilog -t null) to check for syntax errors. Assign a binary syntax score.
  3. Functional simulation: For syntax-valid candidates, run a testbench simulation. Check if output matches the golden reference. Assign a functional score.
  4. Compute weighted reward: Combine syntax and functional scores into a single quality metric per candidate.
  5. RLHF-style training: Use quality scores to weight the loss function — high-quality samples get lower loss weight, effectively reinforcing synthesizable patterns.

Feedback Signal 1: Icarus Verilog Syntax Check

The first quality gate is a syntax check using Icarus Verilog (iverilog), an open-source Verilog compiler. This catches common LLM failure modes like:

  • Missing endmodule keywords
  • Mismatched port declarations
  • Invalid signal widths or types
  • Undefined variables
Python — Syntax Feedback 
import subprocess
import tempfile

def check_verilog_syntax(code: str) -> dict:
    """Run Icarus Verilog syntax check and return score."""
    with tempfile.NamedTemporaryFile(suffix=".v", mode="w", delete=False) as f:
        f.write(code)
        filepath = f.name
    
    result = subprocess.run(
        ["iverilog", "-t", "null", filepath],
        capture_output=True, text=True, timeout=10
    )
    
    syntax_ok = result.returncode == 0
    errors = result.stderr.strip() if not syntax_ok else ""
    
    return {
        "syntax_score": 1.0 if syntax_ok else 0.0,
        "errors": errors,
        "syntax_ok": syntax_ok
    }

Feedback Signal 2: Functional Simulation

Syntax-valid code is further evaluated by running a functional simulation against a testbench. This catches logic errors that syntax checkers cannot:

  • Wrong state machine transitions
  • Off-by-one errors in counters
  • Incorrect reset behavior
  • Race conditions
Python — Functional Simulation Check 
def run_functional_sim(code: str, testbench: str) -> dict:
    """Compile DUT + testbench and run simulation."""
    with tempfile.TemporaryDirectory() as tmpdir:
        dut_path = f"{tmpdir}/dut.v"
        tb_path = f"{tmpdir}/tb.v"
        sim_path = f"{tmpdir}/sim"
        
        with open(dut_path, "w") as f: f.write(code)
        with open(tb_path, "w") as f: f.write(testbench)
        
        # Compile
        compile_result = subprocess.run(
            ["iverilog", "-o", sim_path, dut_path, tb_path],
            capture_output=True, timeout=30
        )
        if compile_result.returncode != 0:
            return {"functional_score": 0.0, "passed": 0, "total": 0}
        
        # Simulate
        sim_result = subprocess.run(
            ["vvp", sim_path],
            capture_output=True, text=True, timeout=60
        )
        
        # Parse PASS/FAIL counts from testbench output
        output = sim_result.stdout
        passed = output.count("PASS")
        failed = output.count("FAIL")
        total = passed + failed
        
        return {
            "functional_score": passed / total if total > 0 else 0.0,
            "passed": passed,
            "total": total
        }

Reward Function

The combined quality score weights functional correctness more heavily than syntax — since syntactically correct but logically wrong code is arguably worse than obvious syntax errors (which are easier to debug):

Python — Quality Reward Function 
def compute_quality_reward(code: str, testbench: str) -> float:
    """Compute the combined quality reward for RTL code."""
    syntax = check_verilog_syntax(code)
    
    if not syntax["syntax_ok"]:
        # Syntax failure: partial credit based on error count
        error_count = len(syntax["errors"].split("\n"))
        return max(0.0, 0.2 - 0.02 * error_count)
    
    functional = run_functional_sim(code, testbench)
    
    # Weighted combination: syntax 30%, functional 70%
    reward = 0.3 * syntax["syntax_score"] + 0.7 * functional["functional_score"]
    
    return reward

def quality_weighted_loss(candidates: list[dict]) -> float:
    """Weight training loss inversely by quality."""
    # High quality → lower loss weight (model already learned this)
    # Low quality → higher loss weight (model needs to learn)
    losses = []
    for c in candidates:
        quality = compute_quality_reward(c["code"], c["testbench"])
        # Invert: reward high quality by down-weighting its loss
        loss_weight = 1.0 - quality * 0.8
        losses.append(c["loss"] * loss_weight)
    return sum(losses) / len(losses)

Privacy Architecture

RTLCoder's local deployment model directly addresses IP privacy concerns — a major barrier to cloud-based EDA AI in the semiconductor industry:

⚠ IP Privacy in EDA

Semiconductor companies cannot send proprietary RTL designs or SPICE netlists to cloud APIs. A single design leak could cost billions in competitive advantage. RTLCoder's 4GB local deployment resolves this: sensitive designs never leave the secure design environment.

EDAid: Divergent Thought Collaboration

EDAid is a multi-agent system built on ChipLlama, a foundation model trained on chip design data. Its key innovation is the Divergent Thought Collaboration architecture — a sophisticated approach to avoiding the failure modes of single-agent systems.

The Divergent Thought Problem

Single-agent systems can get "stuck" — once the agent commits to an erroneous planning pathway (e.g., "this design needs a differential pair"), it becomes hard to escape that local minimum. EDAid addresses this with:

🔀
Diverse CoT Prompts
Each agent in EDAid is given a different few-shot Chain-of-Thought prompt that biases it toward a different design approach. Agent A might be biased toward current-mode designs, Agent B toward voltage-mode, Agent C toward topology exploration.
🎯
Converging on One Goal
Despite divergent starting points, all agents share the same objective function — the PPA targets. The collaboration mechanism synthesizes the best insights from each divergent path.
⚙
ChipLlama Foundation
A Llama-based model fine-tuned specifically on chip design literature, HDL repositories, and EDA tool documentation. All EDAid agents use ChipLlama as their shared reasoning backbone.

Python — EDAid Divergent Thought Implementation 
from langchain_community.llms import Ollama
from langgraph.graph import Send, StateGraph
from typing import Annotated, List
import operator

# Different CoT prompts create divergent reasoning paths
COT_PROMPTS = {
    "differential_pair": """Think step by step as an analog designer who prefers 
    differential pair topologies. Consider source-coupled pairs first.
    Examples: {differential_pair_examples}""",
    
    "folded_cascode": """Think step by step as a designer who favors folded-cascode
    architectures for high gain without compromising bandwidth.
    Examples: {folded_cascode_examples}""",
    
    "current_mirror": """Think step by step focusing on current-mirror biasing
    and systematic design of operating points from bias currents.
    Examples: {current_mirror_examples}"""
}

class EDAidState(TypedDict):
    spec: str
    proposals: Annotated[List[dict], operator.add]  # Collects from all agents

def divergent_agent(state: dict) -> dict:
    """Single divergent agent with a specific CoT bias."""
    cot_type = state["cot_type"]
    cot_prompt = COT_PROMPTS[cot_type].format(**state.get("examples", {}))
    
    chiplllama = Ollama(model="chiplllama-7b")
    
    prompt = f"""{cot_prompt}

Design specification: {state['spec']}

Generate: topology name, transistor sizing rationale, 
estimated PPA, and key design tradeoffs."""
    
    proposal = chiplllama.invoke(prompt)
    ppa = simulate_proposal(proposal)  # Quick pre-simulation
    
    return {"proposals": [{"type": cot_type, "design": proposal, "ppa": ppa}]}

def fan_out_to_divergent_agents(state: EDAidState):
    """Launch all divergent agents in parallel."""
    return [
        Send("divergent_agent", {**state, "cot_type": cot_type})
        for cot_type in COT_PROMPTS.keys()
    ]

def consensus_arbiter(state: EDAidState) -> dict:
    """Synthesize all proposals and select the best."""
    proposals = state["proposals"]
    
    # Score each proposal by PPA
    scored = sorted(proposals, 
                   key=lambda p: p["ppa"]["composite_score"], 
                   reverse=True)
    
    # Extract insights from each divergent path
    synthesis_prompt = f"""Given these {len(proposals)} design proposals:
    {[p['design'] for p in proposals]}
    
    Create an optimal synthesis combining the best aspects of each.
    Winner PPA target: {scored[0]['ppa']}"""
    
    chiplllama = Ollama(model="chiplllama-7b")
    final_design = chiplllama.invoke(synthesis_prompt)
    
    return {"final_design": final_design, "winning_approach": scored[0]["type"]}
