Introduction: Why Agentic Architectures?

The semiconductor industry is in the midst of a profound transformation. As chips scale to hundreds of billions of transistors, the traditional AI-assisted model — where a human engineer orchestrates static Tcl/Python scripts — has broken down. The so-called "Productivity Gap" has emerged: design complexity grows exponentially while engineering productivity grows only linearly.

🔵 Key Insight

Verification now consumes up to 70% of the design cycle. This single bottleneck has driven the shift toward Agentic EDA, where Multi-Agent Systems can autonomously run, evaluate, and iterate on designs.

Unlike early "black box" autonomous agents, 2026-standard systems utilize Agentic Workflows modeled as stateful graphs. This is a critical distinction: the agent's reasoning path is not opaque — it is explicit, inspectable, and controllable. This enables engineers to:

  • Understand why an agent made a specific design choice
  • Intervene at precise points (Human-in-the-Loop)
  • Resume long-running workflows after interruption (persistent checkpointing)
  • Replay historical states for debugging (time-travel debugging)

Agentic Architectures: The Stateful Graph Paradigm

The fundamental building block of 2026-standard agentic systems is the stateful graph. Rather than a simple pipeline (input → LLM → output), a stateful graph maintains persistent state that evolves as agents execute. This allows for iteration, backtracking, and conditional branching.

Stateful Graph Workflows

A stateful graph workflow is a directed graph where:

  • Nodes represent agent actions or tools (e.g., "generate netlist", "run SPICE")
  • Edges represent control flow between nodes (possibly conditional)
  • State is a persistent data structure passed between nodes and modified as the workflow runs

The state typically contains the design specifications, intermediate results, error messages, iteration counter, and any accumulated memory from past runs. This state persists across the entire design closure process — potentially spanning days.

✓ Why This Matters

Persistent state enables long-running agentic workflows like a 48-hour Place & Route run to be resumed after machine failure, without losing the agent's reasoning context.

DAG (Directed Acyclic Graph) Execution

In a DAG, the design flow has no cycles — each task completes before downstream tasks begin. This is suitable for well-defined sequential flows:

DAGs guarantee that every agent executes exactly once, making them ideal for deterministic, well-understood design flows.

Cyclic Loops for Iterative Refinement

Unlike DAGs, cyclic graphs allow agents to loop back when verification fails. This is essential for EDA, where a design rarely passes first-time verification:

⚠ Example: The Sizing Loop

A Sizing Agent computes transistor sizes → SPICE simulation runs → if gain < target, the agent loops back with updated parameters. This cycle may repeat 50–200 times before convergence in analog design.

The key to safe cyclic workflows is having:

  • A termination condition (max iterations, PPA target met)
  • A state delta check (did parameters actually change?)
  • A Critic Agent that validates progress before each cycle

Typed State Schema

The state object passed between agents must have a well-defined, typed schema. This is called Typed Context Engineering and is one of the Twelve Pillars of Production MAS.

Python — State Schema 
from typing import TypedDict, Annotated, List, Optional
from langgraph.graph import StateGraph

class EDADesignState(TypedDict):
    # Input specification
    spec: str
    topology: Optional[str]
    
    # Intermediate results
    netlist: Optional[str]
    simulation_results: Optional[dict]
    
    # Iteration control
    iteration: int
    max_iterations: int
    ppa_targets: dict
    ppa_achieved: Optional[dict]
    
    # Error tracking
    errors: Annotated[List[str], lambda x, y: x + y]
    
    # Memory (agent reasoning traces)
    reasoning_trace: List[dict]

# Build the stateful graph
workflow = StateGraph(EDADesignState)

Using TypedDict with LangGraph's StateGraph gives you compile-time type safety, making the agent's state explicit and auditable.

Key MAS Design Patterns

Production MAS for EDA uses four core architectural patterns. Each pattern addresses a specific class of design challenge. Understanding when to apply each is fundamental to building effective agentic systems.

👑 Pattern 1: Supervisor-Worker
▼

A central orchestrator agent (the Supervisor) decomposes a high-level design intent into concrete sub-tasks and dispatches them to specialized worker agents. The Supervisor tracks progress, handles failures, and decides when the overall objective is met.

🧠
Supervisor Agent
Powered by a capable model (e.g., GPT-5.2 or Claude 4.5). Receives the high-level intent: "Implement a low-power RISC-V core". Decomposes into sub-tasks, assigns priority, and monitors completion.
⚙
Specialized Workers
Domain-expert agents: Synthesis Agent (RTL → gate-level), DFT Agent (Design for Testability), Timing Agent (STA), Power Agent (CPF/UPF). Each is fine-tuned for its specific task.
Python — Supervisor Node Implementation 
from langgraph.graph import StateGraph, END
from langchain_openai import ChatOpenAI

supervisor_llm = ChatOpenAI(model="gpt-5.2", temperature=0)

def supervisor_node(state: EDADesignState) -> dict:
    """Decomposes intent and dispatches to workers."""
    prompt = f"""
    You are the EDA Supervisor. High-level goal: {state['spec']}
    Current iteration: {state['iteration']}
    PPA targets: {state['ppa_targets']}
    
    Determine the next worker to dispatch. 
    Options: synthesis, verification, timing, power, DONE
    Respond with ONLY the worker name.
    """
    response = supervisor_llm.invoke(prompt)
    next_worker = response.content.strip()
    
    return {"next_worker": next_worker, "iteration": state["iteration"] + 1}

def route_to_worker(state: EDADesignState) -> str:
    return state.get("next_worker", END)

workflow = StateGraph(EDADesignState)
workflow.add_node("supervisor", supervisor_node)
workflow.add_node("synthesis", synthesis_agent)
workflow.add_node("verification", verification_agent)
workflow.add_conditional_edges("supervisor", route_to_worker)
🤝 Pattern 2: Consensus-Based Reasoning
▼

Multiple divergent thought agents independently propose different design topologies or solutions. A decision-making agent acts as an arbiter, selecting the optimal proposal based on quantitative PPA (Power, Performance, Area) metrics.

This pattern prevents the system from getting stuck in a local optimum — a critical failure mode in analog topology selection where there are many valid but non-equivalent circuit architectures.

💡
Divergent Agents
Each agent uses different few-shot CoT prompts, different temperature settings, or different model weights to explore distinct areas of the design space in parallel.
⚖
Arbiter Agent
Receives all proposals, runs a comparative PPA evaluation, and selects the winner. May also propose a hybrid solution that combines the best elements of multiple proposals.
📊
PPA Scoring
Power · Performance · Area — the three dimensions of chip design quality. A weighted scoring function converts these into a single comparable metric for decision-making.
Python — Consensus Node 
from langgraph.graph import Send
import asyncio

async def parallel_topology_agents(state: EDADesignState):
    """Launch divergent topology agents in parallel."""
    # Each agent gets a different CoT prompt seed
    seeds = ["differential-pair-centric", "current-mirror-centric", "folded-cascode"]
    
    # Send to parallel workers using LangGraph's Send API
    return [
        Send("topology_agent", {**state, "cot_seed": seed})
        for seed in seeds
    ]

def arbiter_node(state: EDADesignState) -> dict:
    """Select best topology based on PPA scoring."""
    proposals = state.get("topology_proposals", [])
    
    scores = []
    for p in proposals:
        score = (
            0.4 * p["ppa"]["performance_score"] +
            0.35 * (1 - p["ppa"]["power_normalized"]) +
            0.25 * (1 - p["ppa"]["area_normalized"])
        )
        scores.append((score, p))
    
    best = max(scores, key=lambda x: x[0])
    return {"topology": best[1]["topology"], "ppa_achieved": best[1]["ppa"]}
🤲 Pattern 3: Handoff Pattern
▼

Control flows dynamically between specialists based on runtime conditions. A failing agent can hand back control to an earlier specialist with specific error context — enabling targeted recovery rather than full restart.

💜 Example: Sizing Agent Failure

The Sizing Agent attempts to achieve 60dB gain but can only reach 52dB with the current topology. Instead of failing, it hands off back to the Topology Selection Agent with: {"error": "gain_deficit_8dB", "constraint": "power_budget_1mW"}. The Topology Agent then selects a cascode structure and hands forward to Sizing with an updated starting point.

Python — Handoff with Error Context 
def sizing_agent(state: EDADesignState) -> dict:
    """Attempt to size transistors. Hand off on failure."""
    gain_achieved = run_small_signal_sim(state["netlist"])
    gain_target = state["ppa_targets"]["gain_dB"]
    
    if gain_achieved >= gain_target:
        return {"ppa_achieved": {"gain_dB": gain_achieved}, "next": "layout"}
    
    # Handoff back to topology selection with error context
    deficit = gain_target - gain_achieved
    return {
        "errors": [f"gain_deficit_{deficit:.1f}dB"],
        "handoff_context": {
            "failed_topology": state["topology"],
            "deficit": deficit,
            "suggestion": "consider_cascode" if deficit > 5 else "adjust_bias"
        },
        "next": "topology_selection"  # Handoff
    }

def conditional_route(state: EDADesignState) -> str:
    return state.get("next", "sizing")
🔍 Pattern 4: Reflection / Critic Agent
▼

A dedicated Critic Agent is separate from the generator. It receives the output of a generator agent and evaluates it against defined criteria. This separation of concerns is essential for trust and reliability in production systems.

The Critic pattern implements the core principle of 2026 AI engineering: "One agent generates, a separate Critic Agent judges the output."

✍
Generator Agent
Produces netlist, RTL, or layout. Optimized for creativity and coverage of the design space. Uses high temperature for diversity.
🔴
Critic Agent
Evaluates output against specifications, DRC rules, and PPA targets. Uses low temperature for precision. Provides structured feedback for the generator to improve.

LangGraph: Stateful DAGs in Practice

LangGraph is the leading framework for implementing stateful multi-agent workflows. It extends LangChain with the ability to define persistent state graphs that can cycle, branch conditionally, and checkpoint their state automatically.

🔵 LangGraph Key Concepts
  • StateGraph — defines the workflow with a typed state schema
  • Nodes — Python functions that receive state and return partial state updates
  • Edges — define flow between nodes (normal or conditional)
  • Checkpointer — persists state to disk/database after each node
  • Send API — enables parallel fan-out to multiple workers

Complete EDA Workflow Example

Python — Full LangGraph EDA Workflow 
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.sqlite import SqliteSaver

# Initialize persistent checkpointer for long-running P&R
checkpointer = SqliteSaver.from_conn_string("eda_workflow.db")

# Define the workflow graph
workflow = StateGraph(EDADesignState)

# Add nodes
workflow.add_node("spec_parser", parse_specifications)
workflow.add_node("topology_selection", select_topology)
workflow.add_node("sizing", sizing_agent)
workflow.add_node("simulation", run_spice_simulation)
workflow.add_node("critic", evaluate_ppa)
workflow.add_node("layout", physical_layout_agent)

# Define the main flow
workflow.set_entry_point("spec_parser")
workflow.add_edge("spec_parser", "topology_selection")
workflow.add_edge("topology_selection", "sizing")
workflow.add_edge("sizing", "simulation")
workflow.add_edge("simulation", "critic")

# Conditional routing: pass or fail
def ppa_routing(state: EDADesignState) -> str:
    achieved = state.get("ppa_achieved", {})
    targets = state["ppa_targets"]
    
    if all(achieved.get(k, 0) >= v for k, v in targets.items()):
        return "layout"  # All targets met → proceed
    elif state["iteration"] >= state["max_iterations"]:
        return END      # Max iterations → give up
    else:
        return "sizing"  # Re-size with SPICE feedback

workflow.add_conditional_edges("critic", ppa_routing, {
    "layout": "layout",
    "sizing": "sizing",
    END: END
})

workflow.add_edge("layout", END)

# Compile with checkpointer for fault tolerance
app = workflow.compile(checkpointer=checkpointer)

# Run with a thread_id for state persistence
config = {"configurable": {"thread_id": "design-risc-v-001"}}
result = app.invoke({
    "spec": "Low-power RISC-V RV32I core, 100MHz, 28nm",
    "ppa_targets": {"power_mW": 50, "area_um2": 50000, "freq_MHz": 100},
    "iteration": 0,
    "max_iterations": 20,
    "errors": [],
    "reasoning_trace": []
}, config=config)

Time-Travel Debugging

One of LangGraph's most powerful features for EDA is time-travel debugging: the ability to inspect the agent's state at any historical point and understand exactly why a design decision was made.

Python — Time-Travel Debugging 
# Get full history of the design run
history = list(app.get_state_history(config))

print(f"Total steps: {len(history)}")

# Inspect state at iteration 5 (e.g., why did sizing fail?)
state_at_iter5 = history[-5]  # -N goes N steps back
print(f"Node: {state_at_iter5.next}")
print(f"Netlist at that point: {state_at_iter5.values['netlist']}")
print(f"PPA achieved: {state_at_iter5.values['ppa_achieved']}")
print(f"Errors: {state_at_iter5.values['errors']}")

# Fork from a past state and try a different approach
app.update_state(state_at_iter5.config, {
    "topology": "folded_cascode",  # Try different topology
    "errors": []                    # Clear errors
})

# Resume from the fork point
result = app.invoke(None, state_at_iter5.config)
✓ Production Best Practice

Always compile LangGraph workflows with a checkpointer (SqliteSaver for local, PostgresSaver for production). This gives you fault tolerance, audit trails, and time-travel debugging — all essential for production EDA workflows that can run for 24–48 hours.
